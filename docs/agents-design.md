## Модель данных конвейера (сквозная, нужна до агента 2)

Сейчас в репозитории есть только `data/источники.xlsx` (агент 1). Агентам 2–7 нужно ещё минимум два хранилища:

- **`data/статьи/`** — по одному файлу на статью (markdown + frontmatter), поля: `id`, `source_url`, `title`, `category` (пол/возраст/тема — см. открытый вопрос), `status` (`collected` → `selected` → `approved`/`rejected` → `published`), `image_path`, `published_at`, `telegram_message_id`. Файловый подход выбран по аналогии с источниками — человекочитаемо, диффится в git, не требует БД/сервера.
- **`data/подборки/<YYYY-MM-DD>.md`** — сводка дневной подборки агента 3: список из (до) 5 отобранных статей на этот день, для агентов 4/6 и для просмотра пользователем.
- **`data/аналитика.xlsx` или `data/метрики/`** — снимки метрик канала по дням (подписчики, просмотры, реакции по посту), для агента 7.

Без этой модели агенты 2–4 и 6–7 не смогут передавать друг другу состояние — это блокер уровня «до кода», не деталь реализации.

## Полный список проблем (для выбора решения)

1. **Push в отдельную ветку, не в `main`.** Обнаружено на агенте 1: CCR-рутина коммитит в свою ветку (`claude/wizardly-carson-*`), не в `main`, PR не открывает. Без ручного вмешательства каждый день — дублирование работы (агент не видит вчерашние необслитые изменения). Затронет ЛЮБОЙ агент, который пишет в репозиторий: 1, 2, 3, 4, 7 (аналитика), потенциально 5/6, если они тоже код в облачной рутине, а не локальный код.
2. **Финальный список тем публикаций не зафиксирован** (возрастные периоды решены 2026-09-18, см. раздел «Агент 2» выше — эта часть проблемы снята) — категоризация и подборка работают по рабочей черновой схеме тем, которую придётся пересматривать.
3. **Очерёдность агентов внутри суток:** 1→2→3→4 логически последовательны (каждый ждёт выход предыдущего), но заведены (или будут заведены) как независимые рутины по расписанию — нужно либо жёстко развести время запуска с запасом, либо явно передавать управление (агент N сам вызывает/триггерит агента N+1).
4. **Нет модели хранения статей вообще** — `data/статьи/` описана здесь как предложение, не согласована и не создана.
5. **Агент 5 (картинка):** неясно, годится ли уже подключённый коннектор `visualize` для генерации иллюстраций, или нужен отдельный код + отдельный API/ключ (DALL·E, Stability и т.п., с отдельной стоимостью).
6. **Агент 6 (публикация):** Telegram-канал и бот физически не существуют — нужно создать канал, завести бота через @BotFather, выдать токен, добавить бота админом.
7. **Агент 7 (аналитика):** Bot API не отдаёт просмотры постов канала — нужно решить, довольствоваться ли ограниченными метриками (подписчики, реакции) или искать обходной путь (например, ручная выгрузка статистики Telegram самим пользователем на вход агенту).
8. **Хранение секретов для облачных рутин** (Telegram-токен, возможные API-ключи для картинок) — CCR-рутины запускаются в облаке Anthropic, а не на сервере bayesum; нужно решить, где токены живут (переменные окружения рутины, отдельный секрет-хранитель) и кто их туда кладёт.
9. ~~SVG из агента 5 нельзя напрямую отправить в Telegram~~ (`sendPhoto` требует растр) — **промежуточно решено 2026-09-19**: диагностика песочницы показала, что готовых конвертеров/рендереров (`rsvg-convert`, ImageMagick, Chromium и т.п.) в ней нет, но исходящий доступ к PyPI работает, поэтому агент 6 ставит `cairosvg` через `pip install` на лету и конвертирует SVG→PNG перед `sendPhoto`. Публикация — одним сообщением (фото с подписью-карточкой, либо текстом без фото, если конвертация не удалась). Постоянное решение — перенести конвертацию на отдельный сервер проекта (владелец решил завести отдельный сервер именно для Respect, пока не создан).
10. **`WebFetch` заблокирован сетевой политикой облачной песочницы для ВСЕХ проверенных внешних доменов** (обнаружено на первом реальном прогоне агента 2, 2026-09-17: `psyjournals.ru`, `antiage-expert.com`, `seniorgroup.ru`, `britannica.com`, `ncbi.nlm.nih.gov`, `who.int`, `wikipedia.org` — все вернули `EGRESS_BLOCKED`). Работает только `WebSearch` (идёт через инфраструктуру Anthropic, не напрямую). Агент 2 сам адаптировался — использовал `WebSearch` с `allowed_domains` вместо прямого чтения страниц, но это значит, что конспекты статей пишутся по сниппетам поиска, а не по полному тексту — это касается ЛЮБОГО будущего агента, которому нужен прямой доступ к странице (не только агента 2). Решение: либо просить администратора открыть эти домены в egress-политике окружения, либо принять `WebSearch`-only как постоянный режим работы.
11. **Прямой сетевой вызов (`curl`/Bash) к `api.telegram.org` тоже заблокирован политикой песочницы** (обнаружено на первом реальном прогоне агента 6, 2026-09-17: `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHANNEL_ID` заданы корректно, но egress-прокси окружения отвечает `403` на `CONNECT api.telegram.org:443` — «policy denial», см. `curl http://127.0.0.1:39993/__agentproxy/status`). Это отдельная проблема от отсутствия токена (раздел «Агент 6» выше) и от блокировки `WebFetch` (проблема №10) — токены есть, но сама песочница не пускает наружу даже через `Bash`/`curl`. Пока домен `api.telegram.org` не добавлен в egress-allowlist окружения агентов 6 и 7, обе рутины не могут ничего опубликовать/собрать по метрикам независимо от готовности канала и бота — публикация всех 5 одобренных на 2026-09-17 статей не состоялась именно по этой причине, статусы не менялись.
12. ~~Статус `selected` больше никто не проставляет~~ — **решено 2026-09-19**: агент 4 переведён на вход `sorted` (см. раздел «Агент 4» выше), читает рекурсивно по `data/статьи/**`. Отдельный шаг «отобрать 5 на публикацию» в конвейере по-прежнему отсутствует — сейчас агент 4 проверяет на непротиворечивость и одобряет/отклоняет ВСЕ статьи со статусом `sorted`, без ограничения по количеству в день; если нужен явный лимит публикаций в сутки, его придётся вводить отдельно (в агенте 4, 6 или новым агентом).
13. ~~Две независимые живые рутины конкурируют за одни и те же `collected`-статьи в корне `data/статьи/`~~ — **решено 2026-09-19**: владелец переставил связку рецензент/редактор (40–81) на выход агента 4, а не агента 2. Очерёдность (**обновлена повторно в тот же день**, см. ниже): `1 → 2 → 3 → 4 → [писатель40|50|60|70|80] → [агент40|50|60|70|80] → [агент41|51|61|71|81] → 5 → 6 → 7`. Рецензенты/редакторы читают РЕКУРСИВНО `data/статьи/**/*.md` со `status: approved` (а не `collected` из корня), редакторы не меняют `status` (остаётся `approved`, никакого `selected`) — только обогащают `edited_date`/`editor`/`editor_notes`. Подробности и таблица — `docs/architecture-overview.md` и `docs/agent-prompts/README.md`.
